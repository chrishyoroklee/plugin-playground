# Dynamic parameters in plugin formats and hosts: what a modular CLAP plugin (wrapped to VST3 and AUv2) can safely expose

Research date: 2026-11-21. Formatting note: findings are written as "claim. Source: [link]" (no dashes used as separators, per the project owner's writing rule). Source code citations for CLAP and clap-wrapper were read from fresh clones of the `main` branches (clap at commit a47f6ba, 2026-07-27, CLAP 1.2.10; clap-wrapper at commit c3a2531, 2026-11-19), so they describe the code as of those dates.

Options under evaluation: (a) fixed superset of all parameters, (b) fixed generic macro or automation slots whose meaning changes, (c) a parameter list that really changes at runtime.

## 1. CLAP: what the specification says about changing parameters at runtime, and which hosts honour it

### Takeaway
CLAP is the only one of the three formats with a fully specified path for adding and removing parameters (request restart, wait for deactivate, `clear` stale IDs, `rescan(CLAP_PARAM_RESCAN_ALL)`), plus a light path (`RESCAN_INFO`) for renaming and hiding that takes effect immediately. Host support is confirmed in writing only for Bitwig and partly Reaper; nothing reliable was found for FL Studio or Studio One.

### Cited Findings
- The header's scenario VI "Adding or removing parameters" reads: "if the plugin is activated call clap_host->restart()"; "once the plugin isn't active: apply the new state; if a parameter is gone or is created with an id that may have been used before, call clap_host_params.clear(host, param_id, CLAP_PARAM_CLEAR_ALL); call clap_host_params->rescan(CLAP_PARAM_RESCAN_ALL)". Source: [clap/ext/params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- `CLAP_PARAM_RESCAN_INFO` comment, verbatim: "The parameter info did change, use this flag for: name change, module change, is_periodic (flag), is_hidden (flag). New info takes effect immediately." Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- `CLAP_PARAM_RESCAN_ALL` comment, verbatim: "Invalidates everything the host knows about parameters. It can only be used while the plugin is deactivated. If the plugin is activated use clap_host->restart() and delay any change until the host calls clap_plugin->deactivate(). You must use this flag if: some parameters were added or removed; some parameters had critical changes: is_per_note, is_per_key, is_per_channel, is_per_port, is_readonly, is_bypass, is_stepped, is_modulatable (flags), min_value, max_value, cookie." Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- `CLAP_PARAM_RESCAN_TEXT`: "The value to text conversion changed, and the text needs to be rendered again." `CLAP_PARAM_RESCAN_VALUES` covers value changes such as a preset load. Both `rescan` and `clear` are `[main-thread]`. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- So in CLAP, a name change or hide/unhide is a cheap live operation, while a change of range (`min_value`, `max_value`) or of `is_stepped` is in the same heavy class as adding or removing a parameter and needs deactivation. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- `CLAP_PARAM_IS_HIDDEN` comment, verbatim: "The parameter should not be shown to the user, because it is currently not used. It is not necessary to process automation for this parameter." `CLAP_PARAM_IS_ENUM` requires `IS_STEPPED` and a text for every value; `IS_STEPPED` means integer values only. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- `clap_host.request_restart`: "Request the host to deactivate and then reactivate the plugin. The operation may be delayed by the host. [thread-safe]". Source: [clap/host.h](https://github.com/free-audio/clap/blob/main/include/clap/host.h)
- On ranges the header warns: "CLAP allows the plugin to change the parameter range, yet the plugin developer should be aware that doing so isn't without risk... If you want to be 100% certain that the sound will not change with all host, then simply never change the range." It also advises "avoid shrinking parameter ranges" and "if you plan to use adapters for other plugin formats, then you need to pay extra attention to the adapter requirements". Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- A CLAP maintainer (robbert-vdh, issue opened 2023-07-25) clarified: call `rescan(CLAP_PARAM_RESCAN_ALL)` from the main thread to change the number of parameters, but "only actually report a different parameter count after the host has deactivated your plugin (as that could otherwise result in race conditions)". He also called the `clap_host->restart()` wording "a leftover of an older version of the API". Source: [free-audio/clap issue 341](https://github.com/free-audio/clap/issues/341)
- Bitwig, `RESCAN_INFO`: in May 2022 (Bitwig 4.3 beta) Surge's maintainer reported that after a `PARAM_INFO | PARAM_VALUES | PARAM_TEXT` rescan "bitwig shows me the correctly updated param names" when an oscillator type changes, but Bitwig at that time also did a full audio engine restart of the plugin on every such rescan. The issue is closed; the build that fixed the over-eager restart was not confirmed in the text read. Source: [interop-tracker issue 8](https://github.com/free-audio/interop-tracker/issues/8)
- Bitwig, `request_restart`: Bitwig Studio 5.0 and 4.4.10 never deactivated/reactivated the plugin after `request_restart`, which "makes it impossible to reconfigure parameters and notes + audio ports". Bitwig's developer said the fix was merged for 5.1 (2023-09-14); a user still reproduced a variant in 5.1.6 (2024-04), and the developer pointed to a further fix in 5.3.3 (2025-03). Source: [interop-tracker issue 55](https://github.com/free-audio/interop-tracker/issues/55)
- Reaper: the same 2023 report states "REAPER, for example, does call deactivate followed by activate" after `request_restart`. Source: [interop-tracker issue 55](https://github.com/free-audio/interop-tracker/issues/55)
- Reaper, text refresh: a Surge pull request (merged 2026-10-10) reports that after a correct `paramsRescan(VALUES | TEXT | INFO)`, "REAPER did not re-read the parameter text for about ten seconds, until the track control was hovered"; sending a value notification as well made it repaint promptly. Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600)
- A user building a "one type selector plus fixed slots with the hidden flag" CLAP plugin reported (2025-10-30) that the spec's restart then `RESCAN_ALL` flow "works perfectly" in Bitwig for the unwrapped CLAP. Source: [clap-wrapper issue 418](https://github.com/free-audio/clap-wrapper/issues/418)
- Surge XT never uses `RESCAN_ALL`: "All Surge parameters expose a fixed 0..1 range to JUCE with dynamically resolved names, so min_value and max_value never change and CLAP_PARAM_RESCAN_ALL, which would require deactivation, is never needed." Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600)

### Inferences
- For a module chain, CLAP itself would support option (c), but the two things that most often differ between modules (range and stepped-ness) are exactly the "critical changes" that need deactivation. A design that keeps every exposed parameter at a fixed range (for example 0..1 with dynamic value-to-text) can retarget names and visibility with `RESCAN_INFO | RESCAN_TEXT | RESCAN_VALUES` only, which is the Surge pattern.
- Even in the best supported host (Bitwig) the restart path has had bugs across 5.0 to 5.3, so relying on `request_restart` + `RESCAN_ALL` for an everyday user action (swapping a module) is riskier than a one-time fixed layout.

### Gaps
- No reliable written source was found for how FL Studio or Studio One handle `rescan` flags, `clear`, or `IS_HIDDEN` for CLAP plugins. Needs hands-on testing.
- Whether hosts actually hide `CLAP_PARAM_IS_HIDDEN` parameters from automation menus and generic UIs was not confirmed for any host (one 2022 Bitwig report concerns bypass parameters being hidden, which is a different mechanism: [interop-tracker issue 47](https://github.com/free-audio/interop-tracker/issues/47), title only read).
- No host-side statement was found on what happens to existing automation lanes after `clear(CLAP_PARAM_CLEAR_ALL)`.

## 2. VST3: what restartComponent permits, what Steinberg says about changing parameter count, and host behaviour

### Takeaway
Steinberg's documentation says outright that a plugin "must not perform any reconfigurations that lead to a different set of automatable parameters"; titles, defaults, flags and step count may change via `kParamTitlesChanged`, and `kReloadComponent` exists for count changes but is optional for hosts and only documented as working in Bitwig. In practice even title changes are unreliable in Ableton Live during session recall.

### Cited Findings
- Verbatim from the VST3 parameters documentation: "it is not allowed to change this assignment at any time" (parameter ID to parameter), "a plug-in must not perform any reconfigurations that lead to a different set of automatable parameters", "The only allowed variation is the adding or removing of parameters in a future plug-in version", "However, keep in mind that automation data can get lost when parameters are removed." Source: [VST 3 Developer Portal, Parameters and Automation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- For a change of "parameter styles or title or default value of one or multiple parameters, the plug-in must call IComponentHandler::restartComponent (kParamTitlesChanged)" in the UI thread; "The host rescans the ParameterInfos with getParameterInfo." For bulk value changes use `kParamValuesChanged` ("The host invalidates all caches of parameter values and asks the edit controller for the current values"); flags can be combined. Source: [VST 3 Developer Portal, Parameters and Automation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- RestartFlags reference: `kReloadComponent` "The Component should be reloaded" (host unloads and reloads fully); `kParamTitlesChanged` covers titles, defaults, step counts or flags; `kParamIDMappingChanged` is for ID changes when loading state from an older version so the host can remap automation (with `IRemapParamID`, added in SDK 3.7.11). Source: [VST3 interfaces reference](https://steinbergmedia.github.io/vst3_doc/vstinterfaces/namespaceSteinberg_1_1Vst.html); [IRemapParamID, 3.7.11](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Change+History/3.7.11/IRemapParamID.html)
- The hosting FAQ says plug-ins changing their internal/external representation (for example a change of parameter count or number of IO) may use the reload flag, and that a host may return `kNotImplemented` for flags it does not implement; it recommends hosts implement at least `kLatencyChanged` and `kParamValuesChanged`. (Search-snippet level reading; the page was not fetched in full.) Source: [VST 3 Developer Portal, Hosting FAQ](https://steinbergmedia.github.io/vst3_dev_portal/pages/FAQ/Hosting.html)
- `kIsHidden`: "This means that this parameter will NOT be displayed and cannot be changed from outside the plug-in. This requires that kCanAutomate is NOT set and kIsReadOnly is set." `kIsList`: host shows the parameter as a list in generic editors and automation editing. Source: [VST 3 Developer Portal, Parameters and Automation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- Step count: Steinberg's Arne Scheffler stated (2024-05-19) that `stepCount` "can be treated as a kind of flag", so a plugin may signal a step-count change with `kParamTitlesChanged`, and he added that to the docstring (2024-05-23). JUCE added host and client support on its develop branch on 2024-06-27 ("VST3 Client: Update ParameterInfo default value and numSteps when AudioProcessor changes"). Source: [JUCE forum, VST3 parameter info update](https://forum.juce.com/t/vst3-parameter-info-update/59497)
- In the same thread, JUCE's reuk noted (2024-05-13) that nothing in the spec requires hosts to refresh more than titles, defaults and flags; a developer reported step-count changes working in Komplete Kontrol; another (JeffMcClintock, 2024-02-22) warned that changing a range changes how already-recorded automation is interpreted. The use case in the thread was "N automation slots with dynamically assigned parameters". Source: [JUCE forum, VST3 parameter info update](https://forum.juce.com/t/vst3-parameter-info-update/59497)
- Bitwig and `kReloadComponent`: a Bitwig developer (nickallen, 2019-02-05) wrote that Bitwig Studio was updated to support a VST3 whose parameter count changes while processing: plugin calls `restartComponent(kReloadComponent)`, host fades out, `setProcessing(false)`, `setActive(false)`, `setActive(true)`, `setProcessing(true)`, then re-queries parameters. Arne Scheffler confirmed the sequence (2019-02-08) and said `restartComponent` should normally be called only from the UI thread. Old report (2019); no other host is named. Source: [Steinberg forum, call sequence when parameters have changed](https://forums.steinberg.net/t/what-is-the-correct-call-sequence-between-plugin-and-host-when-parameters-have-changed-while-it-is-processing-audio/201851)
- Ableton Live and `kParamTitlesChanged`: a multi-effect developer (2025-07-22) whose parameter names depend on the loaded preset calls `restartComponent(kParamValuesChanged | kParamTitlesChanged)` at the end of `setState`; "most hosts appear to ignore" it during session recall, so automation lanes show generic names (values and ranges were correct). Another developer (2025-08-14) confirmed "Ableton Live ignores restartComponent(kParamTitlesChanged) when called from within setState()"; workaround is to call it again after `setState` returns (timer) or at activation. Steinberg's Yvan said the call inside `setState` is allowed and hosts should support it, and that "some hosts have trouble redrawing automation track parameter names" until the automation track is closed and reopened. Live version not stated. Source: [Steinberg forum, restartComponent(kParamTitlesChanged) during session recall](https://forums.steinberg.net/t/restartcomponent-kparamtitleschanged-during-session-recall/1001494)
- A JUCE developer (2024-10-23) who renames parameters at runtime and calls `updateHostDisplay()` reported that Cubase, Logic and Ableton pick up the new names, while Pro Tools shows new names in its Plug-in Automation window but stale default names in the automation lane drop-down. Host versions and exact formats per host not stated. Source: [JUCE forum, AAX dynamic parameter names](https://forum.juce.com/t/aax-dynamic-parameter-names/63900)
- Cubase with Guitar Rig 5 (older user report): after adding and moving rack components, parameters "start to get confused" (continuous parameters treated as toggles) until the project is saved, closed and reopened. Source: [Steinberg forum, Guitar Rig 5 automation of parameters](https://forums.steinberg.net/t/guitar-rig-5-automation-of-parameters/614191)

### Inferences
- Option (c) on VST3 contradicts Steinberg's written rule and depends on an optional flag (`kReloadComponent`) with exactly one documented supporting host. Options (a) and (b) fit the spec: fixed IDs, with titles, defaults, flags and step counts refreshed through `kParamTitlesChanged`.
- Because VST3 hosts automate normalized 0..1 values, "changing the range" of a slot is a text and step-count change only; old automation keeps its normalized shape but means something different (the JeffMcClintock warning). That is an inherent cost of option (b).
- Any dynamic-name design must re-announce titles after state restore and again a moment later, because of the Live `setState` behaviour.

### Gaps
- No written confirmation was found of how Cubase/Nuendo, Studio One, FL Studio or Reaper react to `kReloadComponent` with a changed parameter count. Unknown, must be tested.
- No per-host matrix for `kParamTitlesChanged` (outside session recall) with version numbers was found for Studio One, FL Studio, Reaper or Bitwig; the evidence is anecdotal forum posts.
- The Hosting FAQ wording on `kReloadComponent` was taken from a search summary, not a full page read.

## 3. Audio Unit v2: ParameterList/ParameterInfo notifications, Logic/GarageBand/MainStage behaviour, auval

### Takeaway
AUv2 has a notification (property change on `kAudioUnitProperty_ParameterList` and `kAudioUnitProperty_ParameterInfo`) but host handling is inconsistent, and Logic and GarageBand additionally restore automation by parameter order rather than ID, which Apple has called a known limitation unlikely to be fixed. A parameter list whose order or membership changes is therefore the highest-risk choice on Logic.

### Cited Findings
- Logic maps saved automation by parameter index: JUCE's reuk reproduced (2021-08-23, Logic 10.6.3) that adding a parameter changes how Logic assigns existing automation, while "Live 11 and Reaper 6.34 recalled automation correctly"; he reproduced it with a JUCE-free AU built on Apple's SDK (2021-12-07), and reported on 2022-01-18 that Apple confirmed it is a known Logic limitation unlikely to be fixed. Final Cut Pro shows the same problem. Source: [JUCE forum, Adding parameters post launch to a plugin?](https://forum.juce.com/t/adding-parameters-post-launch-to-a-plugin/47502)
- Restated in April 2024: "This is a known limitation of Logic, but not one that is likely to be fixed." Parameter order matters only in Logic and GarageBand; other AU hosts use the parameter identifier. The JUCE workaround is `ParameterID{id, versionHint}`: parameters added in later releases get higher hints so they sort after all older ones; hints are used only by the AU wrapper. reuk was unsure whether mid-list insertion works in AUv3. Source: [JUCE forum, Automated parameters are not recalled correctly in Logic/GarageBand](https://forum.juce.com/t/automated-parameters-are-not-recalled-correctly-in-logic-garageband/61031)
- clap-wrapper's own header repeats this: "Parameter order matters in auv2 critically still in logic and garage band, and if you add parameters after a release, you need to order them (alas) even if the ids aren't changed." It offers the `clap.plugin-auv2-param-ordering/0` extension so the plugin can supply the AUv2 order. Source: [clap-wrapper include/clapwrapper/auv2.h](https://github.com/free-audio/clap-wrapper/blob/main/include/clapwrapper/auv2.h)
- Name refresh in Logic: a 2015 JUCE forum post (tadnicol, 2015-12-04/05) reported that Logic Pro 9 and Logic Pro X read parameter names only when the AU is constructed, unless the plugin sends the property-change notifications for parameter list and parameter info (JUCE `updateHostDisplay()`), which "successfully updated the names in Logic". Old report; a 2024 post (see section 2) again says Logic picks up renamed parameters after `updateHostDisplay()`. Source: [JUCE forum, Dynamically alter number of plugin parameters?](https://forum.juce.com/t/dynamically-alter-number-of-plugin-parameters/4745); [JUCE forum, AAX dynamic parameter names](https://forum.juce.com/t/aax-dynamic-parameter-names/63900)
- Which property to notify: u-he's Urs (2013-09-06) suggested `PropertyChanged` on `kAudioUnitProperty_ParameterList` or `kAudioUnitProperty_ParameterInfo` as "the official way" but was "not too optimistic about hosts supporting this"; the asker found `PropertyChanged(kAudioUnitProperty_ParameterInfo, kAudioUnitScope_Global, 0)` worked in AU Lab and did nothing in Reaper at that time. Old report (2013). Source: [KVR, AudioUnit: Change parameter's name and min/max values](https://www.kvraudio.com/forum/viewtopic.php?t=390986)
- Reaper today: per a June 2026 Apple Developer Forums thread, Reaper's developer says Reaper (AUv2 C API) listens for `kAudioUnitEvent_PropertyChange` on global scope for `kAudioUnitProperty_ParameterList` and rescans the parameter list when it fires. The same thread reports an AUv3 plugin with a preset-dependent parameter tree working "well enough" in Logic Pro (Mac and iPad) and AUM, and an Apple engineer says Apple "recently fixed issues where parameter listeners were not notified when the parameter list changed" in the AUv3 to AUv2 bridge. Source: [Apple Developer Forums, kAudioUnitProperty_ParameterList vs AUParameterTree](https://developer.apple.com/forums/thread/829767)
- coreaudio-api list (search-snippet level only; the archive returned HTTP 502 when fetched): a 2013 thread "[AU] Dynamic parameters" reports AU Lab picking up a parameter-list change while Reaper and Ableton Live ignored it, and notes the only guidance found was that one should not add parameters while initialised; a separate thread is titled "[AU] Logic 9 and kAudioUnitProperty_ParameterInfo". Source: [coreaudio-api 2013-03 msg00034](https://lists.apple.com/archives/coreaudio-api/2013/Mar/msg00034.html); [coreaudio-api 2013-03 msg00143](https://lists.apple.com/archives/coreaudio-api/2013/Mar/msg00143.html)
- Logic caches Audio Unit information to speed launch (Apple TN2207, Logic Studio era), which is one reason stale data can persist until a rescan. Source: [Apple TN2207](https://developer.apple.com/library/archive/technotes/tn2207/_index.html)
- Cost of notifying in Logic: clap-wrapper's AUv2 code comments that sending new ParameterList, ParameterInfo and ClassInfo notifications is expensive in Logic: "Logic Pro takes its time over each of them: a few presets stepped through in the plugin's UI backed its UI up by seconds", which is why the wrapper sends only per-parameter value events for a values-only rescan. Source: [clap-wrapper src/wrapasauv2.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasauv2.cpp)
- auval: a 2005 coreaudio-api thread describes auval's "parameters retain value across reset and initialization" test, where auval resets and re-initializes the unit and compares parameter values. (Search-snippet level.) Source: [coreaudio-api 2005-10 msg00298](https://lists.apple.com/archives/coreaudio-api/2005/Oct/msg00298.html)

### Inferences
- On Logic and GarageBand the safe invariant is: the AU parameter list has the same members in the same order for the life of the product, with new parameters only ever appended. That is compatible with options (a) and (b) and incompatible with option (c).
- Renaming a slot at runtime appears workable in Logic (2015 and 2024 reports) but each list/info notification is slow in Logic, so renames should be batched (one notification per module change, not one per parameter).
- A changing parameter count is likely to interact badly with auval's retain-across-reset test if the count differs between passes; a fixed list avoids the question.

### Gaps
- No source was found that documents how Logic's automation lanes and Smart Controls, GarageBand, or MainStage react when an AU's parameter count changes while loaded, or whether Smart Control mappings follow a renamed parameter. Not confirmed.
- No authoritative list of what current auval (AUv2) checks about parameter lists was found; Apple's TN2104 and the auval source were not retrieved.
- The two coreaudio-api posts could not be read in full (server error), so their detail is unverified.

## 4. How clap-wrapper translates CLAP parameter rescans to VST3 and AUv2, and known limitations

### Takeaway
clap-wrapper forwards renames and value refreshes well enough, but it does not give VST3 hosts any "parameter count changed" signal: on `RESCAN_ALL` it rebuilds its internal parameter container and sends only `kMidiCCAssignmentChanged`, never `kReloadComponent`. On AUv2 it rebuilds the list and fires ParameterList, ParameterInfo and ClassInfo property changes. There is an open issue (418) about the restart then rescan flow hanging in a VST3 host.

### Cited Findings
All of the following are from direct reading of the wrapper source at commit c3a2531 (2026-11-19).
- VST3 `ClapAsVst3::param_rescan`: `CLAP_PARAM_RESCAN_ALL` calls `setupParameters()` (which does `parameters.removeAll()` then re-adds every CLAP parameter and rebuilds units) and sets only `Vst::RestartFlags::kMidiCCAssignmentChanged`. `RESCAN_VALUES` maps to `kParamValuesChanged`. `RESCAN_INFO` maps to `kParamValuesChanged | kParamTitlesChanged`. The combined flags are passed to `componentHandler->restartComponent(vstflags)`. `kReloadComponent` is never sent anywhere in the wrapper. Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- VST3: `CLAP_PARAM_RESCAN_TEXT` on its own maps to no VST3 flag; the function returns early when `vstflags == 0`, so a text-only rescan is silently dropped. Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- VST3: on `RESCAN_INFO` without `RESCAN_ALL` the wrapper re-reads only the title of each existing parameter; the code comment says "the name and module can also change. For now, don't rebuild the unit tree with modules but do rescan the name". Flags such as hidden and the short title are not refreshed in that path. Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- VST3 flag mapping at parameter creation: `CLAP_PARAM_IS_HIDDEN` to `kIsHidden`, `IS_BYPASS` to `kIsBypass`, `IS_AUTOMATABLE` to `kCanAutomate`, `IS_READONLY` to `kIsReadOnly`, `IS_ENUM` to `kIsList`. The wrapper does not strip `kCanAutomate` or add `kIsReadOnly` for hidden parameters, although Steinberg's doc says `kIsHidden` "requires that kCanAutomate is NOT set and kIsReadOnly is set". The VST3 title is "module/name" unless too long. Units are empty ("CLAP has no unit for parameter values"). Source: [clap-wrapper src/detail/vst3/parameter.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/detail/vst3/parameter.cpp); [VST 3 Developer Portal](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- VST3 `param_clear`: `CLAP_PARAM_CLEAR_ALL` removes the parameter from the wrapper's container (ID masked with `0x7FFFFFFF`); the comment says "all other flags can not be really mapped to VST3 functions". Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- VST3 `request_restart`: sets a flag that is serviced later with `restartComponent(kIoChanged | kLatencyChanged)`. Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- The wrapper already guards against rescans arriving inside plugin `init()` and inside state `load()` before the host has supplied a component handler, and notes "a restart is not free" for hosts. Source: [clap-wrapper src/wrapasvst3.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasvst3.cpp)
- AUv2 `WrapAsAUV2::param_rescan`: always re-runs `setupParameters()`. If only `RESCAN_VALUES` is set, it sends a `kAudioUnitEvent_ParameterValueChange` per parameter. If any of `RESCAN_ALL`, `RESCAN_INFO`, `RESCAN_TEXT` is set, it calls `PropertyChanged` for `kAudioUnitProperty_ParameterList`, `kAudioUnitProperty_ParameterInfo` and `kAudioUnitProperty_ClassInfo` on global scope. A finer per-parameter notification attempt is left disabled with the comment "This code doesn't actually do what we want". Source: [clap-wrapper src/wrapasauv2.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasauv2.cpp)
- AUv2 flag mapping: a `CLAP_PARAM_IS_HIDDEN` parameter gets neither `kAudioUnitParameterFlag_IsReadable` nor `IsWritable`; non-automatable becomes `NonRealTime`; stepped becomes Indexed (or Boolean for a plain 0/1 non-enum). Source: [clap-wrapper src/detail/auv2/parameter.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/detail/auv2/parameter.cpp)
- AUv2 `request_restart`: "AU has no host-facing 'reinitialize me', but it needs none: the wrapper owns the CLAP's activate/deactivate itself", so it deactivates and reactivates the CLAP under a still-initialized AU, rendering silence meanwhile. Source: [clap-wrapper src/wrapasauv2.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasauv2.cpp)
- AUv2 parameter order can be fixed by the plugin through `clap_plugin_auv2_param_ordering` (`get_param_order`), intended for keeping Logic/GarageBand automation intact when parameters are added in a later release. Source: [clap-wrapper include/clapwrapper/auv2.h](https://github.com/free-audio/clap-wrapper/blob/main/include/clapwrapper/auv2.h)
- Open issue 418 (opened 2025-10-30, still open at research time): a plugin using "a constant number of allocated parameters by adding the hidden flag to unused parameter slots", with per-type names, defaults and ranges, found that the spec's flow (request restart, then `rescan` inside `activate`) misbehaves through the VST3 wrapper; in the JUCE AudioPluginHost "an indefinite freeze happens on the call to restartComponent". Workaround: use `clap_host::request_callback` and rescan from the main-thread callback. The same flow "works perfectly" as native CLAP in Bitwig. Source: [clap-wrapper issue 418](https://github.com/free-audio/clap-wrapper/issues/418)
- Open issue 303 (opened 2024-09-04): wrapped VST3 in Ableton Live 11.3.10 and 12.0 receives the full set of default parameter values in the first process block after a state load, overwriting loaded values unless the plugin guards against it. Source: [clap-wrapper issue 303](https://github.com/free-audio/clap-wrapper/issues/303)
- Other wrapper issues that touched parameter and state sync in 2026 (titles only): 490 "AUv2: state restore broken in Logic Pro ... AU param cache is not resynced after state load" (closed), 475 "VST3: state not restored in Ableton Live" (closed), 528 "Linux: onIdle() only runs while the plug-in editor is open, so request_restart / request_callback / flush are dropped headless" (open). Source: [clap-wrapper issues](https://github.com/free-audio/clap-wrapper/issues)

### Inferences
- Through clap-wrapper, a real change in parameter count (option c) reaches a VST3 host as, at best, `kMidiCCAssignmentChanged` plus whatever value/title flags the plugin also set. A VST3 host has no documented reason to re-read `getParameterCount()` on those flags, so the host's list can go stale against the wrapper's rebuilt container. Option (c) is effectively unsupported for the VST3 target with the stock wrapper.
- To toggle hidden state or step count on VST3 through the wrapper, the plugin has to send `RESCAN_ALL | RESCAN_INFO` (ALL to rebuild the Vst3Parameter objects with new flags, INFO to get `kParamTitlesChanged` emitted). This is an inference from the code paths, not a documented recipe, and `RESCAN_ALL` formally requires the plugin to be deactivated.
- For value text that changes with module type, always pair `RESCAN_TEXT` with `RESCAN_INFO` or `RESCAN_VALUES`, since text-only rescans are dropped on VST3.
- The pattern in issue 418 (fixed slot count plus hidden flag plus a type selector) is the same design as options (a)/(b), and its reporter hit wrapper bugs only when using the restart path, which supports doing all rescans from a main-thread callback while keeping ranges fixed so that restart is never needed.

### Gaps
- No clap-wrapper documentation page describing rescan translation was found; the behaviour above comes from reading code and can change between commits.
- The AUv2 `param_clear` implementation and the AAX path were not examined in detail.
- No report was found of anyone shipping a wrapped plugin that changes parameter count in Logic, Cubase, Live or Studio One.

## 5. What shipping modular plugins do

### Takeaway
Every modular product for which documentation was found uses a fixed host-facing list: a small set of always-present macros (4 to 16) plus a fixed pool of assignable automation slots (40 to several hundred). None was found that changes its parameter count at runtime.

### Cited Findings
- Kilohearts Snap Heap, Multipass, Phase Plant: "Due to the open modular nature of our host plugins, your DAW cannot keep a complete list of all available parameters." Always-present parameters (for example Master Pitch in Phase Plant, and the macros) automate normally; every other module parameter must be assigned by right-click to one of 64 automation slots, and the slot takes the name of the assigned function. Renaming a macro is saved in the preset and "immediately shown in your DAW". Source: [Kilohearts docs, Host Plugins](https://kilohearts.com/docs/host_plugins)
- Phase Plant has eight macro knobs under the patch name. Source: [Kilohearts docs, Phase Plant](https://kilohearts.com/docs/phase_plant)
- Native Instruments Guitar Rig (manual copyright 2024) reports a fixed list of 512 automation IDs: 1 to 16 fixed to the 16 Macros; 17 to 256 dynamically mapped to parameters of components in the Rack; 257 to 276 fixed to Header parameters; 277 to 384 fixed to Rack Tools; 385 to 512 dynamically mapped to Global FX components. Dynamic IDs are preset-specific and "automatically adapt to changes in the Rack". Automation can be disabled per component (its parameters leave the reported list). "Clean up Automation List" remaps dynamic IDs top to bottom, with the warning: "If you have already automated these parameters in your project, the automation will not work correctly any more." A parameter assigned to a Macro ignores automation on its own ID. Source: [Guitar Rig manual, Automation and MIDI control](https://docs.native-instruments.com/online-guides/guitar-rig-manual/en/automation-and-midi-control)
- Kontakt: community posts describe host automation as 512 numbered slots ("Host Automation #0511" style names) to which the user drags assignments. Community-level source, not the manual. Source: [NI community, Problem with Host Automation in Ableton Live 12](https://community.native-instruments.com/discussion/43325/problem-with-host-automation-in-ableton-live-12)
- MeldaProduction MXXX: 16 multiparameters per the KVR product listing; multiparameters are the vendor's mechanism for controlling several internal parameters with one automatable control. Source: [KVR, MXXX product page](https://www.kvraudio.com/product/mxxx-by-meldaproduction); [MeldaProduction, multiparameters introduction](https://www.meldaproduction.com/tutorials/multiparameters-introduction)
- Blue Cat PatchWork: a forum post quoting the manual says 40 mappable controls named "Control 01" to "Control 40"; hosted plug-in parameters are mapped to them for automation and control surfaces, and since v2.6 one control can drive several parameters. Forum-level source; current count not verified. Source: [KVR, Patchwork and controller surface for the plugins?](https://www.kvraudio.com/forum/viewtopic.php?p=7009021); [Blue Cat Audio blog, hosted plug-ins automation](https://www.bluecataudio.com/Blog/tip-of-the-day/hosted-plug-ins-automation/)
- Vital: exactly 4 macros, as fixed parameters `macro_control_1` to `macro_control_4` (`kNumMacros = 4`), within a fixed full parameter list. Source: [Vital synth_parameters.cpp](https://github.com/mtytel/vital/blob/main/src/common/synth_parameters.cpp); [Vital synth_constants.h](https://github.com/mtytel/vital/blob/main/src/common/synth_constants.h)
- Surge XT (full synth): fixed superset; every parameter is exposed with a fixed 0..1 range and "dynamically resolved names", and the plugin tells the host with `paramsRescan(VALUES | TEXT | INFO)` when a type change renames or re-texts parameters (oscillator type, filter type and so on). Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600); [interop-tracker issue 8](https://github.com/free-audio/interop-tracker/issues/8)
- Surge XT Effects (the standalone FX plugin, one swappable effect type): 12 generic host parameters named "FX Parameter 1" to "FX Parameter 12" with IDs `fx_parm_N`, range 0..1. Source: [surge src/surge-fx/SurgeFXProcessor.cpp](https://github.com/surge-synthesizer/surge/blob/main/src/surge-fx/SurgeFXProcessor.cpp)
- Arturia Pigments: a KVR poster reports 2226 automatable parameters (forum claim, not official), meaning a very large fixed superset alongside its macros. Source: [KVR forum post](https://www.kvraudio.com/forum/viewtopic.php?p=8695069)
- Serum: a third-party support article states Serum 2 has more macro slots than Serum 1 (it gives 6 versus 3, which conflicts with the commonly shown four macros of Serum 1 in a 2022 Computer Music tutorial). Conflicting, not verified against the Xfer manual. Source: [Jamstik support article](https://support.jamstik.com/hc/en-us/articles/36105116351373); contradicted in part by [Computer Music tutorial](https://www.pressreader.com/australia/computer-music/20221130/282647511524403)
- Bitwig's own devices: users describe per-device Remote Controls organised in pages of 8, which replaced the 8 fixed macros per device of Bitwig 1.x. Forum-level source. Source: [KVR, Device panel sharing thread](https://www.kvraudio.com/forum/viewtopic.php?p=9087317)

### Inferences
- Industry practice converges on a hybrid of options (a) and (b): a few fixed, renameable macros that always exist, plus a fixed pool of slots. Vendors with very large open-ended module sets (Kilohearts, NI, Blue Cat) use user-assigned or auto-assigned slots because a superset is impossible; vendors with a bounded structure (Vital, Surge, Pigments) expose a fixed superset.
- The product in question is bounded and small: about 7 module types, each with at most 4 dials and 1 switch. A positional superset (per chain position: type selector, bypass, 4 dials, 1 switch) or a per-type superset (7 types x 5 = 35 parameters plus order/enable parameters) is far below the sizes that pushed Kilohearts and NI to slot pools. A superset of this size is closer to the Surge/Vital case than to the Snap Heap case.
- Guitar Rig's "dynamic IDs adapt to the rack" model is the documented source of the worst user-facing failure in this survey (cleanup breaks existing automation; Cubase confusion after reordering), which argues for binding slots to stable identities rather than to chain position if chain order is user-editable.

### Gaps
- Official macro counts for Serum 2, Arturia Pigments, Snap Heap and Multipass were not confirmed from vendor manuals.
- Kontakt's 512 host automation IDs and PatchWork's 40 controls rest on forum posts, not current manuals.
- How MXXX names its multiparameters to the host, and its total exposed parameter count, were not confirmed.
- No documentation was found for any shipping plugin that uses a truly dynamic parameter count in production across VST3 and AU.

## 6. Documented failure modes when parameters change

### Takeaway
The documented failures are: automation re-pointed to the wrong parameter (Logic, by index), stale or generic names in automation lanes (Live on session recall, Pro Tools lane menu, Reaper until hover), wrong parameter type after reordering (Cubase with Guitar Rig), automation that silently stops matching after a remap, host freezes or restarts on rescan, and values overwritten after state load.

### Cited Findings
- Re-pointed automation: in Logic, after a plugin update that added parameters, "a pitch lane was read as parameter 8, volume". Cause: Logic restores automation by parameter index. Source: [JUCE forum, 2024](https://forum.juce.com/t/automated-parameters-are-not-recalled-correctly-in-logic-garageband/61031)
- Lost automation: Steinberg's own text, "automation data can get lost when parameters are removed". Source: [VST 3 Developer Portal](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- Broken automation after remap: Guitar Rig's cleanup function warning, "If you have already automated these parameters in your project, the automation will not work correctly any more." Source: [Guitar Rig manual](https://docs.native-instruments.com/online-guides/guitar-rig-manual/en/automation-and-midi-control)
- Wrong names in lanes after project load: Ableton Live ignores `kParamTitlesChanged` sent from inside `setState`, so preset-dependent names appear as generic names after session recall (2025). Source: [Steinberg forum](https://forums.steinberg.net/t/restartcomponent-kparamtitleschanged-during-session-recall/1001494)
- Partial name refresh: Pro Tools shows new names in the Plug-in Automation window but stale names in the automation lane drop-down (2024). Source: [JUCE forum](https://forum.juce.com/t/aax-dynamic-parameter-names/63900)
- Delayed text refresh: Reaper did not re-read CLAP parameter text for about ten seconds after a correct rescan, until hover (2026). Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600)
- Wrong parameter type: Cubase treated continuous Guitar Rig 5 parameters as toggles after rack components were added or moved, until project save, close and reopen. Source: [Steinberg forum](https://forums.steinberg.net/t/guitar-rig-5-automation-of-parameters/614191)
- Changed meaning of recorded automation when a range changes: raised as the core objection to dynamic ranges (JeffMcClintock, 2024-02-22); CLAP's header makes the same point ("avoid shrinking parameter ranges, they are very likely to change the sound"). Source: [JUCE forum](https://forum.juce.com/t/vst3-parameter-info-update/59497); [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- Engine restarts and glitches on rename: Bitwig 4.3 beta restarted the whole plugin on an info/text rescan (2022); a JUCE thread reports the JUCE VST3 wrapper historically bundled a latency-changed flag into every `updateHostDisplay`, which some hosts treat as a latency change (older thread). Source: [interop-tracker issue 8](https://github.com/free-audio/interop-tracker/issues/8); [JUCE forum, updateHostDisplay() VST3](https://forum.juce.com/t/updatehostdisplay-vst3/13338)
- Host freeze: JUCE AudioPluginHost froze when the wrapped VST3 called `restartComponent` from within `activate` during a restart-driven rescan (2025). Source: [clap-wrapper issue 418](https://github.com/free-audio/clap-wrapper/issues/418)
- Preset/state recall: Live 11.3.10 and 12.0 push default parameter values into the first process block after state load for a wrapped VST3 (2024); JUCE's docs warn that "replacing the parameter tree after construction will crash many hosts". Source: [clap-wrapper issue 303](https://github.com/free-audio/clap-wrapper/issues/303); [JUCE AudioProcessor reference](https://docs.juce.com/master/classAudioProcessor.html)
- UI stall in Logic from repeated list/info/class-info notifications. Source: [clap-wrapper src/wrapasauv2.cpp](https://github.com/free-audio/clap-wrapper/blob/main/src/wrapasauv2.cpp)

### Inferences
- Most of these failures are name or text staleness (cosmetic, recoverable) when the list is fixed, but become data loss (re-pointed or dropped automation) when membership or order changes. That asymmetry is the main argument for (a) or (b) over (c).
- Option (b) (slots that change meaning) inherits the "changed meaning of recorded automation" failure whenever the user swaps the module behind a slot that already has automation. Option (a) with per-type parameters avoids that, at the cost of more parameters and lanes that point at an inactive module.

### Gaps
- No documented report was found on control-surface mapping failures specific to dynamic parameters (for example Logic Smart Controls, Mackie/EuCon pages, NKS), beyond the note that step-count updates help NKS/Komplete Kontrol when "runtime-assignable automation" is used ([JUCE forum](https://forum.juce.com/t/vst3-parameter-info-update/59497)).
- No documented case of a saved project failing to load because a plugin's parameter count differed at load time was found; the risk is inferred from the Logic index behaviour.

## 7. Recommended practice for stable IDs, ordering, later additions, hidden parameters, and stepped parameters for module choice and order

### Takeaway
Developer consensus across formats is: declare everything up front, never change an ID's meaning or the list order, append new parameters only at the end (with explicit AU ordering), keep ranges fixed, and express "what is active" with names, text, hidden flags and stepped selector parameters rather than with list changes.

### Cited Findings
- IDs are permanent: VST3 requires a unique 32-bit ID per parameter and "it is not allowed to change this assignment at any time"; adding or removing parameters is allowed only "in a future plug-in version". If IDs must change between versions, VST3 3.7.11 added `IRemapParamID` with `kParamIDMappingChanged`. Source: [VST 3 Developer Portal](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html); [IRemapParamID](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Change+History/3.7.11/IRemapParamID.html)
- CLAP: if an ID is retired or reused, call `clear(param_id, CLAP_PARAM_CLEAR_ALL)` before the rescan so the host drops stale references. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- Order is part of the contract on AU: keep all previously shipped parameters in their original order and append new ones; in JUCE this is done with increasing `versionHint`, in clap-wrapper with the `clap.plugin-auv2-param-ordering/0` extension ("make sure your old version param subset retains the param id ordering"). Source: [JUCE forum, 2024](https://forum.juce.com/t/automated-parameters-are-not-recalled-correctly-in-logic-garageband/61031); [clap-wrapper auv2.h](https://github.com/free-audio/clap-wrapper/blob/main/include/clapwrapper/auv2.h)
- Store a state version number and migrate on load, and test in Logic and Final Cut Pro before shipping a parameter-list change. Source: [JUCE forum, 2021](https://forum.juce.com/t/adding-parameters-post-launch-to-a-plugin/47502)
- Oversized fixed list as the classic workaround: register every possible parameter up front, blank or generic-name unused ones, never move indexes (JUCE forum, 2010, still echoed by JUCE's current docs, which say to edit names in the existing tree and call `updateHostDisplay()` rather than replace the tree). Old post, same advice today. Source: [JUCE forum, 2010 thread](https://forum.juce.com/t/dynamically-alter-number-of-plugin-parameters/4745); [JUCE AudioProcessor reference](https://docs.juce.com/master/classAudioProcessor.html)
- Keep ranges fixed and move meaning into text: Surge exposes every parameter as 0..1 with dynamic names and value text so that `RESCAN_ALL` is never needed. CLAP's header: "simply never change the range" if the sound must never change. Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600); [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h)
- After a rename or text change, also send a value notification, because hosts may defer re-reading text until something makes them repaint. Source: [surge PR 8600](https://github.com/surge-synthesizer/surge/pull/8600)
- Re-announce titles after state load is complete (timer or at activation), not only inside `setState`. Source: [Steinberg forum, 2025](https://forums.steinberg.net/t/restartcomponent-kparamtitleschanged-during-session-recall/1001494)
- Hidden/inactive parameters: CLAP `IS_HIDDEN` is defined for exactly this ("currently not used", no automation processing required) and can be toggled live with `RESCAN_INFO`. VST3 `kIsHidden` is stricter: not displayed, not changeable from outside, must not have `kCanAutomate` and must have `kIsReadOnly`. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h); [VST 3 Developer Portal](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)
- Stepped and enumerated parameters: CLAP `IS_ENUM` needs `IS_STEPPED` and a text for every value, and stepped values should be stored as plain values by hosts; VST3 expresses the same with `stepCount` plus `kIsList`; clap-wrapper maps `IS_ENUM` to `kIsList` on VST3 and to an Indexed unit on AUv2. Changing `stepCount` at runtime is now officially signalled by `kParamTitlesChanged` (Steinberg, May 2024), but changing `is_stepped` in CLAP needs `RESCAN_ALL`. Source: [params.h](https://github.com/free-audio/clap/blob/main/include/clap/ext/params.h); [clap-wrapper parameter.cpp (VST3)](https://github.com/free-audio/clap-wrapper/blob/main/src/detail/vst3/parameter.cpp); [clap-wrapper parameter.cpp (AUv2)](https://github.com/free-audio/clap-wrapper/blob/main/src/detail/auv2/parameter.cpp); [JUCE forum](https://forum.juce.com/t/vst3-parameter-info-update/59497)
- VST3 forbids automating a selector that changes other automatable parameters only in the specific case of program-change parameters: a `kIsProgramChange` parameter "is not allowed to be automated when the affected parameters are flagged as automatable as well". Source: [VST 3 Developer Portal](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Parameters+Automation/Index.html)

### Inferences
- A design consistent with all of the above for this product: declare a fixed list once (every ID, order, range, stepped flag and enum size frozen for the product's life), with (1) per-position enum parameters for module type with a fixed value list that is only ever appended to, (2) module order expressed through those per-position type selectors or separate stepped parameters rather than through list order, (3) dial parameters at a fixed 0..1 range with dynamic value text, and (4) the one option switch declared as an enum with a fixed maximum step count large enough for the widest module, since `is_stepped` and ranges cannot change cheaply.
- Whether dials belong to a chain position (slot semantics, option b) or to a module type (superset semantics, option a) is the real decision. Position-bound slots keep the list small but change meaning when the user swaps or reorders modules, which silently reinterprets existing automation. Type-bound parameters keep automation meaning stable across reordering, need roughly 7 x 5 = 35 parameters, and only become awkward if two instances of the same module type are allowed in one chain.
- Prefer renaming over hiding on VST3: the wrapper only refreshes titles on `RESCAN_INFO`, and VST3's hidden flag is defined as non-automatable and read-only, which does not match "temporarily inactive but still has automation".
- Module-type and module-order selectors should probably be non-automatable (or at least clearly documented as not intended for automation), because automating them renames and re-texts other parameters mid-playback, which triggers every refresh failure in section 6. This is by analogy with the VST3 program-change rule, not a direct spec requirement.
- Reserve growth room now: append-only is the only safe evolution on Logic, so plan the final order with future modules in mind, and add explicit AUv2 ordering from the first release.

### Gaps
- No published guidance was found on how many spare or reserved parameters modular plugin vendors pre-allocate for future modules.
- No source was found comparing position-bound versus type-bound parameter schemes directly; the trade-off above is reasoned from the failure reports.
- No host documentation was found stating how automation lanes behave for a VST3 parameter that toggles `kIsHidden` while it has recorded automation.
