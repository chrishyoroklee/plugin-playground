# Distribution, installers, code signing and notarization for a free audio plugin (solo developer, as of November 2026)

Research date: 2026-11-21. Costs, eligibility and operating system behaviour change often. Every dated claim below carries the date of the page it came from. Items marked "local check" were observed on the research machine (macOS 26.5.2, build 25F84) and have no URL.

Sources are given as "Source: [name](url)" at the end of each bullet.

## 1. macOS: what is needed to ship a notarized .pkg containing an app and plugin bundles, and what Gatekeeper does in macOS 14, 15 and 26

### Takeaway
One paid Apple Developer Program membership (99 USD per year, individuals can enroll) gives both certificates that are needed: Developer ID Application for the app and every plugin bundle, Developer ID Installer for the .pkg. Sign with hardened runtime and a secure timestamp, sign the .pkg, submit it once with `notarytool`, staple it. Since macOS 15 an un-notarized download can only be opened by going to System Settings, Privacy & Security, Open Anyway. That path still exists on macOS 26, but the first dialog now only offers Move to Trash or Done.

### Cited Findings

Membership and cost
- "The Apple Developer Program is 99 USD per membership year, or in local currency where available." Enrollment is open to individuals or organizations "in more than 220 countries or regions". Fee waivers exist only for "eligible nonprofit organizations, accredited educational institutions, and government entities", so not for an individual. Source: [Apple Developer Program, What's included](https://developer.apple.com/programs/whats-included/) (fetched 2026-11-21)
- Organization enrollment needs a D-U-N-S number (can take a few days); individual enrollment does not. Apple approval takes about 1 to 2 days. Developers must re-accept updated agreements or notarization stalls. Source: [Moonbase, Code signing audio plugins in 2025, a round-up](https://moonbase.sh/articles/code-signing-audio-plugins-in-2025-a-round-up/) (Sudara, published 2025-03-06, updated 2025-04-09)
- A free Apple Account can sign with an "Apple Development" identity through Xcode's Personal Team, but that is not Developer ID and cannot be notarized (see the notarization rule below). Source: [Apple Developer Forums thread 782645, Quinn of Apple DTS](https://developer.apple.com/forums/thread/782645) (April to May 2025)

Notarization requirements (Apple primary documentation)
- The notary service requires: valid code signatures on all executables; "Use a 'Developer ID' application, kernel extension, system extension, or installer certificate for your code-signing signature. (Don't use a Mac Distribution, ad hoc, Apple Developer, or local development certificate.)"; "Enable the Hardened Runtime capability"; "Include a secure timestamp"; no `com.apple.security.get-task-allow` entitlement set to true; "Link against the macOS 10.9 or later SDK". Source: [Apple, Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- `notarytool` has been required in place of `altool` since 2023-11-01. Source: [Apple, Notarizing macOS software before distribution](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution)
- Accepted uploads: "disk images (UDIF format), signed flat installer packages, and ZIP archives". "The notary service generates a ticket for the top-level file that you specify, as well as for each nested file. For example, if you submit a disk image that contains a signed installer package with an app bundle inside, the notarization service generates tickets for the disk image, installer package, and app bundle." So one submission of the .pkg covers the app and the plugin bundles inside it. Source: [Apple, Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- Stapling works on "your app, bundle, disk image, or flat installer package". A ZIP cannot be stapled, and standalone binaries cannot be stapled. Source: [Apple, Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- "Notarization completes for most software within 5 minutes, and for 98 percent of software within 15 minutes." The same page mentions a limit of 75 notarizations per day. Source: [Apple, Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- Credentials: Apple's page documents Apple ID plus app-specific password plus team ID (`--apple-id`, `--password`, `--team-id`), optionally stored with `notarytool store-credentials`. Source: [Apple, Customizing the notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)
- Local check (notarytool 1.1.2 on macOS 26.5.2, `xcrun notarytool submit --help`): the tool also accepts an App Store Connect API key with `--key`, `--key-id`, and `--issuer` ("Required for Team API Keys. Do not provide for Individual API Keys.").

Certificates, signing commands and CI automation (practitioner sources)
- Developer ID Application signs plugin bundles and apps; Developer ID Installer signs a .pkg distributed from a website; "Mac Installer Distribution" is for the Mac App Store only. Mixing these up is the most common mistake. Sources: [melatonin.dev, How to code sign and notarize macOS audio plugins in CI](https://melatonin.dev/blog/how-to-code-sign-and-notarize-macos-audio-plugins-in-ci/) (first published 2022-09-23, updated 2026); [Moonbase round-up](https://moonbase.sh/articles/code-signing-audio-plugins-in-2025-a-round-up/)
- Recipe for CI: export each certificate from Xcode as a password-protected .p12, base64-encode it into a GitHub secret, import it in the job with `Apple-Actions/import-codesign-certs`, sign each bundle with `codesign --force -s "<identity>" --strict --options=runtime --timestamp`, notarize only the outermost container with `xcrun notarytool submit ... --wait`, then `xcrun stapler staple`. Secrets used: `DEV_ID_APP_CERT`, `DEV_ID_APP_PASSWORD`, `DEVELOPER_ID_APPLICATION`, `TEAM_ID`, `NOTARIZATION_USERNAME`, `NOTARIZATION_PASSWORD`, plus three more for the installer certificate. Source: [melatonin.dev](https://melatonin.dev/blog/how-to-code-sign-and-notarize-macos-audio-plugins-in-ci/)
- Gotchas from the same article: "Invalid" notarization is usually an unsigned or untimestamped nested binary (read the log with `notarytool log`); HTTP 403 means the membership lapsed; error 1048 or a stall means a pending agreement; changing the Apple ID password invalidates the app-specific password; modifying Info.plist after signing gives a "damaged or incomplete" error. Source: [melatonin.dev](https://melatonin.dev/blog/how-to-code-sign-and-notarize-macos-audio-plugins-in-ci/)
- Pamplejuce (JUCE template, current main branch): imports both certificates with `sudara/basic-macos-keychain-action@v1`, signs VST3, AU, CLAP and Standalone with `--deep --strict --options=runtime --timestamp`, builds one component package per format with `pkgbuild`, combines them with `productbuild --sign "<Developer ID Installer>" --timestamp`, runs `xcrun notarytool submit --wait` with Apple ID, app-specific password and team ID, then staples the .pkg. Source: [Pamplejuce build_and_test.yml](https://raw.githubusercontent.com/sudara/pamplejuce/main/.github/workflows/build_and_test.yml) (fetched 2026-11-21)
- Apple's first-party `pkgbuild` and `productbuild` are the recommended way to make the installer; sign each component first, then build the package. Source: [Moonbase, How to make macOS installers for JUCE projects with pkgbuild and productbuild](https://moonbase.sh/articles/how-to-make-macos-installers-for-juce-projects-with-pkgbuild-and-productbuild/) (2025-01-21)

Entitlements
- Library validation is switched on by the hardened runtime; a process with it on "can only load code signed by Apple or with the same Team ID as the executable". "Leave library validation enabled. Only disable it if your app needs to load plug-ins from other third-party developers." Disabling it also makes Gatekeeper run a more extensive check of the app. Source: [Apple Developer Forums thread 706414, Quinn of Apple DTS](https://developer.apple.com/forums/thread/706414)
- Apple's entitlement reference describes `com.apple.security.cs.disable-library-validation` as meant for programs that load plug-ins signed by other developers. Source: [Apple, Disable Library Validation Entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.cs.disable-library-validation)
- Surge XT applies an entitlements file only to its standalone app flavors, not to the plugin bundles. Source: [Surge make_installer.sh](https://raw.githubusercontent.com/surge-synthesizer/surge/main/scripts/installer_mac/make_installer.sh)

Gatekeeper behaviour by version
- macOS 15 Sequoia (Apple, 2024-08-06): "users will no longer be able to Control-click to override Gatekeeper when opening software that isn't signed correctly or notarized. They'll need to visit System Settings > Privacy & Security to review security information for software before allowing it to run." Source: [Apple Developer News, Updates to runtime protection in macOS Sequoia](https://developer.apple.com/news/?id=saqachfa)
- Current Apple support steps (page dated 2026-05-27): try to open the app once, then System Settings, Privacy & Security, scroll down, "Open Anyway", then confirm "Open". The app is then saved as an exception. Source: [Apple Support 102445, Safely open apps on your Mac](https://support.apple.com/en-us/102445)
- Apple's Mac User Guide says the Open Anyway button "is available for about an hour after you try to open the app". Source: [Apple Mac User Guide, Open a Mac app from an unknown developer (macOS 26)](https://support.apple.com/en-ke/guide/mac-help/mh40617/26/mac/26) (seen via search summary, not fetched in full)
- macOS 14 Sonoma and earlier: the Control-click, Open shortcut still worked, and it was removed in Sequoia. Sources: [MacRumors, 2024-08-06](https://www.macrumors.com/2024/08/06/macos-sequoia-gatekeeper-security-change/); [Michael Tsai, 2024-07-05](https://mjtsai.com/blog/2024/07/05/sequoia-removes-gatekeeper-contextual-menu-override)
- macOS 26 Tahoe (tests on 26.6.1, 2026-08-11): "All executable code must now be signed, even if only with an ad hoc signature, and the signature must not be broken." A quarantined ad hoc signed app was offered Move to Trash at launch; the same app without the quarantine attribute "launched normally with no warning". Code with a broken signature was blocked in every condition. `spctl --master-disable` is no longer supported. Source: [Eclectic Light Company, How can you run code that hasn't been notarised?](https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/)
- On macOS 26.3 a developer reported that `spctl --type install` rejected a notarized .pkg, which suggests `spctl` is not a reliable verification step for packages on Tahoe. Source: [Apple Developer Forums thread 817887](https://developer.apple.com/forums/thread/817887) (title seen in search, thread not read)
- Apple's platform guide states Gatekeeper applies to "apps, plug-ins, and installer packages from outside the App Store". Source: [Apple Platform Security, Gatekeeper and runtime protection](https://support.apple.com/guide/platform-support/supbb8762b42/web)

### Inferences
- For this product the signing order is: sign each template plugin bundle inside the helper app (Developer ID Application, hardened runtime, timestamp), sign the helper app, build the .pkg, sign it with Developer ID Installer, notarize the .pkg, staple the .pkg. One notarization submission covers everything nested.
- The project's own packaging script already has a branch that adds `--options runtime --timestamp` when the identity is not ad hoc (scripts/plugin.py line 724), so the work left is certificates, secrets and the notarize and staple steps.
- An App Store Connect API key is a better CI credential than an app-specific password, since it does not break when the Apple ID password changes. Apple's web page does not document this for notarytool, the tool's own help does.
- With an unsigned .pkg, every macOS 15 and 26 user has to complete a four step detour through System Settings within about an hour of the first attempt. That is the cost being bought off for 99 USD per year.

### Gaps
- Validity period of Developer ID certificates was not confirmed from a primary source. The Moonbase article says certificates "expire after one year"; I could not check this against Apple's certificate documentation in this session. Treat as unverified.
- The exact wording of the macOS 26 dialogs for an unsigned .pkg (as opposed to an app) was not found. The Eclectic Light tests used apps.
- Apple's compare-memberships page did not render its table, so "notarization requires paid membership" rests on the notarization page's rule that only Developer ID certificates are accepted, plus practitioner sources.
- The Apple pricing is quoted in USD; local-currency price for the developer's country was not looked up.

## 2. macOS plugins: ad hoc or unsigned plugins in hosts, bundles created or modified on the user's machine, and precedent

### Takeaway
A plugin bundle written by a program on the user's own machine carries no quarantine flag, so Gatekeeper does not assess it, and a valid ad hoc signature satisfies the Apple silicon rule that all code be signed. Whether it loads then depends on the host: hosts that load third-party plugins either lack library validation or carry the disable-library-validation entitlement, and Apple's own Audio Unit hosting services carry it. This is not confirmed for every host from primary documentation and should be tested host by host; note that the locally re-signed copy is no longer covered by the developer's Developer ID or notarization ticket.

### Cited Findings
- With hardened runtime and library validation on, a process can load only platform code or code with the same Team ID. "If you're ad-hoc signed then you have no Team ID and thus, if you have library validation enabled, you can only load platform libraries." The workaround is the `com.apple.security.cs.disable-library-validation` entitlement on the loading process. Quinn also warns: "If you ad-hoc sign code you will run into numerous weird problems like this" and notes ad hoc code "doesn't have a stable designated requirement". Source: [Apple Developer Forums thread 782645](https://developer.apple.com/forums/thread/782645) (April to May 2025)
- Apple DTS: disabling library validation only makes sense "if your app loads plug-ins from other third-party developers". Source: [Apple Developer Forums thread 706414](https://developer.apple.com/forums/thread/706414)
- Local check (macOS 26.5.2, `codesign -d --entitlements -`): Apple's `AUHostingServiceXPC.xpc` and `AUHostingServiceXPC_arrow.xpc` in AudioToolbox carry `com.apple.security.cs.disable-library-validation` and `allow-unsigned-executable-memory`. `/usr/bin/auvaltool` carries `disable-library-validation`. GarageBand.app is sandboxed, has the hardened runtime flag, and carries the private entitlement `com.apple.private.security.clear-library-validation`. Logic Pro.app on this machine is sandboxed and its code directory shows `flags=0x0(none)`, that is, no hardened runtime flag on the main executable.
- On Apple silicon, Logic Pro runs plug-ins out of process: "Logic Pro sandboxes plug-ins, but only on Apple Silicon." Source: [JUCE forum, JUCE and macOS 11 / ARM](https://forum.juce.com/t/juce-and-macos-11-arm/40285?page=6) (forum post, secondary)
- Logic and auval reject Audio Unit codes without a capital letter: a user's exported plugin was flagged in Logic until the plugin ID and manufacturer ID contained an uppercase character. Source: [KVR, PNS export, unidentified developer](https://www.kvraudio.com/forum/viewtopic.php?p=8461654) (2022-06-27)
- Tahoe tests: an ad hoc signed app with no quarantine attribute runs without any warning; a bundle whose signature is broken does not run at all. Source: [Eclectic Light Company, 2026-08-11](https://eclecticlight.co/2026/08/11/how-can-you-run-code-that-hasnt-been-notarised/)
- Modifying Info.plist after signing invalidates the signature ("damaged or incomplete"). This is why a bundle whose Info.plist is rewritten must be re-signed. Source: [melatonin.dev](https://melatonin.dev/blog/how-to-code-sign-and-notarize-macos-audio-plugins-in-ci/)
- The project's current state (local repository, native/README.md): generated plugins "carry no quarantine flag, because a program on the machine wrote them", generated Audio Units pass `auval`, and the README states that nobody has yet loaded one in a DAW ("Nobody has yet loaded one in", line 207). Local file, no URL.

Precedent: products that generate plugin bundles on the user's machine
- Blue Cat Audio Plug'n Script exports a user's script as a standalone VST, VST3 or AU plugin on the user's machine. In a 2022 to 2023 support thread, an exported plugin loaded in the author's own Cubase 12 but showed as "Unidentified developer" (greyed out in Vienna Ensemble Pro, absent in Cubase) on a friend's Mac. Blue Cat's answer: macOS "requires that you codesign all your binaries with a valid Apple developer id" for distribution to other machines, the workaround for recipients is `xattr -rd com.apple.quarantine`, and "there is no known way around" Apple's certificate check. Blue Cat also warned that copying files can destroy a signature, so distribute in a disk image or zip. Source: [KVR, PNS export, unidentified developer](https://www.kvraudio.com/forum/viewtopic.php?p=8461654) (2022-06-25 to 2023-03-18)
- The Plug'n Script 3.6 release thread mentions manual steps for code signing macOS plugins exported from Windows, which confirms the vendor documents that exported plugins must be signed by the exporting user. Source: [KVR, Plug'n Script 3.6 released](https://www.kvraudio.com/forum/viewtopic.php?p=9210269) (seen in search results, not read in full)

### Inferences
- The generate-on-device design works for the person who generated the plugin, for the same reason the Plug'n Script author could load his own export: no quarantine flag, valid (ad hoc) signature, and hosts that do not enforce same-team library validation on plugins.
- The same Plug'n Script thread is the clearest warning for the "redistribute" feature: a generated plugin sent to another Mac arrives quarantined with only an ad hoc signature, and the recipient gets "unidentified developer" or a silent failure. A user without their own Developer ID cannot fix that. Sharing the recipe (the data file) and letting the recipient's helper app generate the plugin locally avoids the problem entirely.
- The template inside the notarized .pkg is Developer ID signed, but the generated copy is not: once Info.plist changes and the copy is re-signed ad hoc, it has no Team ID and no notarization ticket. Notarizing the installer therefore improves trust in the installer and helper, and does nothing for generated plugins.
- The helper app itself must stay able to run `codesign` on the user's machine. `codesign` ships with macOS (it is how the project works today), so no Xcode install should be needed; this is an inference from current behaviour, not from documentation.
- Hosts with hardened runtime and library validation left on cannot load any third-party plugin at all, so mainstream DAWs must have opted out. The risky cases are sandboxed or security-hardened hosts and enterprise-managed Macs.
- An alternative that avoids re-signing: keep the signed bundle byte-identical and have it read its identity from a file outside the bundle. That does not work for Audio Units, VST3 class IDs or CLAP IDs as registered by Info.plist, which is presumably why the project rewrites Info.plist.

### Gaps
- No Apple documentation was found that states outright "an ad hoc signed, unquarantined Audio Unit loads in Logic Pro on Apple silicon". The evidence is the entitlements of Apple's hosting services (local check), `auval` passing in the project, and the Tahoe tests on apps.
- Entitlements of Ableton Live, Bitwig, REAPER, Cubase, FL Studio and Studio One on macOS were not checked (none were installed on the research machine). Needs a hands-on test matrix.
- I found no statement on whether Apple could tighten AUHostingService policy in a future release. Any such change would break this design; flag as a standing risk.
- Other possible precedents (HISE, Cmajor, Faust, plugdata exports, Max/RNBO, MATLAB Audio Toolbox) compile or export plugins on the user's machine, but I did not confirm their macOS signing guidance in this session.

## 3. Windows: code signing options and costs in 2026, and how SmartScreen reputation works

### Takeaway
Signing never removes the SmartScreen warning immediately any more: since 2024 EV certificates get the same treatment as OV, and reputation builds per file and per publisher over "several weeks and hundreds of clean installs". The cheapest paid route, Azure Artifact Signing at about 9.99 USD per month, is open to individuals only in the USA and Canada; elsewhere an individual needs a traditional certificate (about 150 to 300 USD per year, key on hardware or cloud HSM), Certum's Open Source certificate (about 69 EUR), or free signing through SignPath Foundation if the project qualifies as open source.

### Cited Findings

SmartScreen (Microsoft primary documentation, page dated 2026-05-04, updated 2026-08-17)
- SmartScreen weighs publisher reputation and file hash reputation. "Even when signed, a newly created binary could still show a SmartScreen warning until its hash or publisher certificate accumulates sufficient evidence of positive reputation." Source: [Microsoft Learn, SmartScreen reputation for Windows app developers](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- "When a file is not signed, SmartScreen reputation must build for each new version of your files, starting with zero reputation." Signed files let reputation carry to new versions signed by the same identity. Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- "EV certificates no longer bypass SmartScreen... Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- "There is no exact threshold, but it can take several weeks and hundreds of clean installs from a wide audience." There is no mechanism to submit a file for consumer reputation review. Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Unsigned: "Windows protected your PC"; the user must choose "Run anyway"; enterprise policy can block entirely. Signed with OV or EV: still a warning at first, but "verified publisher name is displayed". Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- "On Windows 11 devices, the Smart App Control feature may supersede SmartScreen Application Reputation. Smart App Control will block execution of unsigned files unless the file has a positive reputation. Smart App Control signature checks apply to all executable files, not just those downloaded from the Internet." Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- Reputation does not transfer from an old certificate to a renewed one, even with the same publisher name (reported in a 2026 Microsoft Q&A thread, not official documentation). Source: [Microsoft Q&A 5900208](https://learn.microsoft.com/en-us/answers/questions/5900208/smartscreen-reputation-reset-following-ev-certific)

Options and prices (Microsoft comparison page dated 2026-10-29, updated 2026-11-10)
- Azure Artifact Signing (formerly Trusted Signing): "~$9.99/month"; no hardware token; "Reputation builds over time; initial warnings expected". OV certificate: "$150-300/year", worldwide, same SmartScreen behaviour. EV: "$400+/year", "Same as OV since 2024". Self-signed and unsigned: not suitable for public distribution. Source: [Microsoft Learn, Code signing options for Windows app developers](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- "As of June 2023, the CA/Browser Forum requires private keys for OV certificates to be stored on a hardware security module (HSM) or hardware token. Most CAs provide a compatible USB token or cloud HSM option." Source: [Microsoft Learn, Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- Microsoft Store: MSIX packages are re-signed by Microsoft for free and never show SmartScreen; this path does not fit an installer that writes VST3 and CLAP files into shared plugin folders. Source: [Microsoft Learn, Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- From 2026-02-27 a code signing certificate may be valid for at most 459 days, so multi-year purchases need reissues. Source: [Certum, code signing offer](https://www.certum.eu/en/cert_offer_code_signing/) (seen via search summary)

Azure Artifact Signing eligibility (two Microsoft pages disagree on organizations, agree on individuals)
- Quickstart (ms.date 2026-05-21, page updated 2026-11-20): "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. Individual developers must be located in the United States or Canada." Source: [Microsoft Learn, Quickstart: Set up Artifact Signing](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)
- Comparison page (2026-10-29): "available to organizations in the USA, Canada, the European Union, and the United Kingdom. Individual developers are currently limited to the USA and Canada." Source: [Microsoft Learn, Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options). This conflicts with the longer country list in the quickstart; the quickstart was updated more recently.
- Individual validation uses the Azure billing account, which "must have an Account Type of Individual", and the legal name and address must match a government ID; verification runs through a third-party ID check (AU10TIX) and Microsoft Authenticator. The certificate shows name, city, state and country; "Your email address and street address aren't included in the certificate." Source: [Microsoft Learn, Quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart)
- Tiers: Basic includes 5,000 signatures per month and one certificate profile of each type; Premium includes 100,000 and ten. Source: [Azure, Artifact Signing pricing](https://azure.microsoft.com/en-us/pricing/details/artifact-signing/) (prices rendered as placeholders when fetched; the 9.99 USD figure comes from the Microsoft Learn pages above)
- User reports confirm the restriction in practice: a France-based individual could not select France (March 2026), and Australia was unsupported for organizations in March 2026 (it appears in the later quickstart list). Sources: [Microsoft Q&A 5810735](https://learn.microsoft.com/en-us/answers/questions/5810735/cant-create-a-new-trusted-signing-individual-ident); [Microsoft Q&A 5834570](https://learn.microsoft.com/en-us/answers/questions/5834570/when-will-azure-artifact-signing-support-australia)
- Pamplejuce signs its Inno Setup output in GitHub Actions with `azure/artifact-signing-action@v2`, using six secrets (tenant ID, client ID, client secret, endpoint, account name, certificate profile name). Source: [Pamplejuce build_and_test.yml](https://raw.githubusercontent.com/sudara/pamplejuce/main/.github/workflows/build_and_test.yml)
- Conflict: the Moonbase round-up (April 2025) says Azure Trusted Signing gives "instant reputation" that removes the SmartScreen warning, and that organizations needed 3 or more years of history. Microsoft's 2026 pages say the opposite on reputation: "Azure Artifact Signing does not provide instant SmartScreen trust". Prefer Microsoft's current text. Sources: [Moonbase round-up](https://moonbase.sh/articles/code-signing-audio-plugins-in-2025-a-round-up/); [Microsoft Learn, Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)

SignPath Foundation (free, open source only)
- Microsoft itself points to it: "SignPath Foundation offers free code signing for qualifying open-source projects." Source: [Microsoft Learn, Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- Conditions: OSI-approved license "without commercial dual-licensing for all components"; "The project may not contain any proprietary, non open-source component"; actively maintained and already released; "we require a certain verifiable reputation"; binaries "must be built from source code in a verifiable way"; each release manually approved by a team member; multi-factor authentication for all team members; a published "Code signing policy" page with a credit line and team roles; software that provides installation must also provide uninstallation. Source: [SignPath Foundation terms](https://signpath.org/terms)
- "The code signing certificate is issued to SignPath Foundation. This means that SignPath Foundation is the publisher." So the SmartScreen and UAC publisher name would be SignPath Foundation, not the developer. Source: [SignPath Foundation terms](https://signpath.org/terms)

Certum Open Source Code Signing
- The shop lists the Open Source Code Signing set (certificate, cryptographic card, card reader) at 69.00 EUR. The certificate is issued to a natural person, with the name "prefixed with 'Open Source Developer'". It requires the card, a reader and Certum's proCertum CardManager software. Source: [Certum shop, Open Source Code Signing set](https://shop.certum.eu/open-source-code-signing.html) (fetched 2026-11-21)
- A cloud variant (SimplySign) exists as a separate product; its price could not be read reliably. Source: [Certum shop, Open Source Code Signing on SimplySign](https://shop.certum.eu/open-source-code-signing-on-simplysign.html) (not fetched in full)

### Inferences
- For an individual outside the USA and Canada, Azure Artifact Signing is closed unless a legal entity is registered in a supported country. The realistic choices are SignPath Foundation (free, publisher shown as SignPath Foundation, needs an open source license and some existing reputation), Certum Open Source (cheapest paid, key on a physical card or Certum's cloud, shows the person's own name with an "Open Source Developer" prefix), or a standard OV or individual-validation certificate with a cloud HSM.
- A physical smart card cannot be used from GitHub-hosted runners. CI signing needs either a cloud key service (Azure Artifact Signing, Certum SimplySign, a CA's cloud HSM, SignPath) or a self-hosted runner.
- Signing the Inno Setup .exe will not make the blue SmartScreen dialog disappear on day one. What changes at once: the dialog shows a verified publisher name instead of "Unknown publisher", reputation carries across releases instead of resetting with every build, and Smart App Control on Windows 11 stops blocking the file outright.
- Because unsigned files restart reputation with every new hash, a project that rebuilds its installer often (nightly or per commit) never earns reputation while unsigned. Keeping a stable release file for longer helps even before signing.
- Smart App Control checks every executable file, not only downloads. Unsigned VST3 and CLAP DLLs installed by the setup program could be blocked on machines with Smart App Control on, so the plugin binaries should be signed as well as the installer. The Windows side of the product apparently also creates plugins on the user's machine; if those are copies of a signed DLL with a separate data file, the signature survives, but any modification of the DLL itself would break it.

### Gaps
- Whether SmartScreen treats Azure Artifact Signing certificates more favourably than CA certificates in practice is disputed between practitioner reports and Microsoft's documentation; no measurement was found.
- Exact current prices at DigiCert, Sectigo, SSL.com and GlobalSign were not collected; the 150 to 300 USD (OV) and 400+ USD (EV) ranges are Microsoft's summary.
- Certum's renewal price, cloud price and validity term were not confirmed. A third-party review cited an older "from $49.99" figure that I could not date.
- The quickstart's individual-developer rule may change; Microsoft Q&A answers on this topic were partly AI-generated and are only indicative.
- Whether SignPath Foundation would accept this project depends on its license and "verifiable reputation", which is assessed case by case.

## 4. Windows plugins: install locations, per-user folders, and installer conventions

### Takeaway
The expected locations are `C:\Program Files\Common Files\VST3` and `C:\Program Files\Common Files\CLAP`, which need administrator rights. Per-user folders exist in both specifications (`%LOCALAPPDATA%\Programs\Common\VST3` and `...\CLAP`), but host support for the per-user VST3 folder is uneven, so the system-wide folders remain the safe default. Inno Setup is the common choice among small plugin makers.

### Cited Findings
- VST3 on Windows, in priority order: user `%LOCALAPPDATA%/Programs/Common/VST3/` ("Mainly for development"), global `/Program Files/Common Files/VST3/`, then the host application's own `VST3` folder. "First found plug-in (for a given Processor UID) has to be used." Hosts scan these folders recursively; links and shortcuts are allowed. Source: [Steinberg VST 3 Developer Portal, Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html)
- CLAP on Windows: `%COMMONPROGRAMFILES%\CLAP` and `%LOCALAPPDATA%\Programs\Common\CLAP`; a host must also query the `CLAP_PATH` environment variable. Source: [CLAP entry.h](https://raw.githubusercontent.com/free-audio/clap/main/include/clap/entry.h)
- Steinberg said when adding the per-user location that "it will take some time until VST3 hosts support this new location on Windows". Source: [Steinberg forums, Installing VST3 in a Windows user folder](https://forums.steinberg.net/t/installing-vst3-in-a-windows-user-folder/742861) (seen via search summary)
- A September 2026 forum survey (one user's own checks, unverified): REAPER scans both per-user folders plus `%CLAP_PATH%`; Bitwig scans both per-user folders; Ableton Live scans `%COMMONPROGRAMFILES%\VST3` plus one user-set custom folder; FL Studio does not allow custom VST3 search paths. An Image-Line staff member replied that FL Studio reads `CLAP_PATH`. Source: [Image-Line forum, VST3 and CLAP search paths?](https://forum.image-line.com/viewtopic.php?p=2075782) (2026-09-21 to 2026-09-30)
- Renoise users report it does not find VST3 plugins outside `Common Files\VST3`; the JUCE forum has a request to add `%LOCALAPPDATA%` to JUCE's default VST3 scan locations, which implies JUCE-based hosts did not scan it by default at the time. Sources: [Renoise forum](https://forum.renoise.com/t/vst3-plugins-not-recognized-if-not-in-common-files-vst3/62893?page=2); [JUCE forum](https://forum.juce.com/t/getdefaultlocationstosearch-should-include-localappdata-for-vst3-plugin-scan-path/49735)
- Installer tools in use: Pamplejuce uses Inno Setup (`iscc "packaging\installer.iss"`); Surge XT installs Inno Setup in its release workflow and ships `-setup.exe` plus a portable zip and a "pluginsonly" zip; ChowDSP BYOD builds with Inno Setup 6; plugdata builds an .msi with WiX Toolset 3.14. Sources: [Pamplejuce workflow](https://raw.githubusercontent.com/sudara/pamplejuce/main/.github/workflows/build_and_test.yml); [Surge build-release.yml](https://raw.githubusercontent.com/surge-synthesizer/surge/main/.github/workflows/build-release.yml); [BYOD build_win_installer.sh](https://raw.githubusercontent.com/Chowdhury-DSP/BYOD/main/installers/windows/build_win_installer.sh); [plugdata package-Windows.sh](https://raw.githubusercontent.com/plugdata-team/plugdata/develop/.github/scripts/package-Windows.sh)

### Inferences
- A per-user, no-administrator install is possible for CLAP in most CLAP hosts and for VST3 in REAPER and Bitwig, but not reliably in Ableton Live, FL Studio or Renoise. The setup program should default to the Common Files folders (with a UAC prompt) and could offer per-user as an option.
- This matters for the generate-on-device feature on Windows: if the helper writes new plugins into `Program Files\Common Files`, it needs elevation every time. Writing generated plugins to the per-user folders avoids elevation but loses hosts that do not scan them. A design choice to surface in the plan.
- Inno Setup fits the existing toolchain and matches peer practice; there is no evidence that plugin users expect MSI. Inno Setup also creates an uninstaller entry in Windows Settings automatically, which meets the SignPath uninstall condition.

### Gaps
- Cubase, Studio One, Cakewalk and Reason behaviour for the per-user VST3 folder was not confirmed.
- The Image-Line thread was only partly visible; FL Studio's exact default VST3 paths were not confirmed from its manual.
- No survey was found of installer technology share among plugin vendors; the claim that Inno Setup is common rests on four open source examples and forum mentions. NSIS usage was not checked.

## 5. Linux: what users expect and where plugins go

### Takeaway
Linux audio users are comfortable with a tarball that copies bundles into per-user folders (`~/.vst3`, `~/.clap`, `~/.lv2`), and larger projects add a .deb. Plugins installed this way are generally invisible to Flatpak-sandboxed hosts, which is a known ecosystem limit and not something an installer script can fix.

### Cited Findings
- VST3 on Linux, in priority order: `$HOME/.vst3/`, `/usr/lib64/vst3/` (Fedora), `/usr/lib/vst3/`, `/usr/local/lib64/vst3/`, `/usr/local/lib/vst3/`, then the application folder. Source: [Steinberg VST 3 Developer Portal, Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html)
- CLAP on Linux: `~/.clap` and `/usr/lib/clap`, plus `CLAP_PATH`. Source: [CLAP entry.h](https://raw.githubusercontent.com/free-audio/clap/main/include/clap/entry.h)
- LV2 per-user folder is `~/.lv2`; Cardinal's install guide tells users to move bundles into `~/.lv2`, `~/.vst`, `~/.vst3`. Source: [DISTRHO Cardinal wiki, Install](https://github.com/DISTRHO/Cardinal/wiki/Install)
- u-he ships Linux plugins as a `.tar.xz` with an install script that copies files to the expected locations. Source: [u-he FAQ, install paths on Linux](https://u-he.com/support/faq/compatibility/install-paths-linux/)
- Arch packaging guidelines: system destinations `/usr/lib/vst3/`, `/usr/lib/clap/`, `/usr/lib/lv2/`, with package names suffixed by format (for example `name-clap`, `name-vst3`). Source: [ArchWiki, Audio plugins package guidelines](https://wiki.archlinux.org/title/Audio_plugins_package_guidelines)
- What peers ship: Surge XT offers `.deb`, `.rpm`, `.tar.gz` and a "pluginsonly" tarball; plugdata offers per-distribution `.tar.xz` files (Arch, Debian, Fedora 41 and 42, openSUSE, Ubuntu 22.04 and 24.04); ChowDSP BYOD offers a `.deb`; Dexed offers a zip. Sources: [Surge releases](https://github.com/surge-synthesizer/surge/releases); [plugdata releases](https://github.com/plugdata-team/plugdata/releases); [BYOD releases](https://github.com/Chowdhury-DSP/BYOD/releases); [Dexed releases](https://github.com/asb2m10/dexed/releases) (asset lists read through the GitHub API on 2026-11-21)
- Flatpak: a Flatpak DAW "won't by default be able to find any plugins external from their container"; plugins for Flatpak hosts are packaged as `org.freedesktop.LinuxAudio.Plugins.*` extensions that must match the host's runtime branch; community advice is "the best experience is to be had by only using Flatpak plugins" with a Flatpak DAW. Sources: [KVR, The linux DAW thread](https://www.kvraudio.com/forum/viewtopic.php?p=8598070); [Flathub discourse, Proposal for audio plugins](https://discourse.flathub.org/t/proposal-for-audio-plugins/399); [Ardour forum, Flatpak plugin paths](https://discourse.ardour.org/t/changing-ladspa-lv2-plugin-paths-flatpak/109209)

### Inferences
- The current tarball plus install script matches user expectations and u-he's precedent. Installing to the per-user folders needs no root and suits the generate-on-device feature.
- plugdata's per-distribution tarballs suggest binary compatibility (glibc and library versions) is the practical Linux problem, more than packaging format. Building on an old baseline distribution is the usual answer; this is general practice and was not sourced here.
- A Flatpak cannot realistically contain this product, since it must write new plugin bundles into the user's plugin folders. An AUR package is typically contributed by the community once a project has users.
- There is no code signing expectation on Linux; publishing checksums (Surge and Dexed attach `artifact_sha256sum.txt`) is the visible norm.

### Gaps
- No data on what share of Linux DAW users run Flatpak hosts.
- Whether a Flatpak host can be given access to `~/.vst3` through a permission override was not confirmed.
- LV2 system paths were taken from Arch guidelines and community guides, not from the LV2 specification itself.

## 6. What small and open source plugin developers actually do

### Takeaway
The standard indie setup is Apple Developer Program plus `pkgbuild`/`productbuild` plus `notarytool` in GitHub Actions on macOS, and Inno Setup on Windows, signed with Azure Artifact Signing where the developer is eligible. Open source projects almost all sign and notarize on macOS (through a maintainer's personal Developer ID), while several still ship unsigned Windows installers. Yearly cost is about 99 USD for macOS alone, about 219 USD with Azure signing.

### Cited Findings
- Cost summary from a widely cited practitioner guide: macOS 99 USD per year; Azure Trusted Signing 9.99 USD per month; third-party Windows certificates about 200 to 300 USD per year. "Your programs won't run on other machines without notarization." Sign the Windows binaries too, so Defender does not flag them. Source: [Moonbase round-up](https://moonbase.sh/articles/code-signing-audio-plugins-in-2025-a-round-up/) (2025-03-06, updated 2025-04-09)
- On Windows, "some tell users to click past the SmartScreen warning and still earn a living, but many have adopted code signing since Azure launched" (paraphrase of the article's account). Source: [Moonbase round-up](https://moonbase.sh/articles/code-signing-audio-plugins-in-2025-a-round-up/)
- A HISE forum developer: "locally I'm building an inno installer for windows and accepting the smartscreen issue for now." Source: [HISE forum post 122158](https://forum.hise.audio/post/122158)
- Pamplejuce: macOS pkg signed, notarized and stapled; Windows Inno Setup .exe signed with Azure Artifact Signing; all in one GitHub Actions workflow. Source: [Pamplejuce workflow](https://raw.githubusercontent.com/sudara/pamplejuce/main/.github/workflows/build_and_test.yml)
- Surge XT: macOS uses `pkgbuild` per format, `productbuild` with a distribution.xml, signs with `codesign --force -s ... -o runtime --deep`, puts the .pkg in a .dmg, signs, notarizes (`notarytool` with Apple ID, team ID and app-specific password) and staples the .dmg. Certificates are imported with `apple-actions/import-codesign-certs`. Signing only runs when the certificate secret is present, so forks still build. Sources: [Surge make_installer.sh](https://raw.githubusercontent.com/surge-synthesizer/surge/main/scripts/installer_mac/make_installer.sh); [Surge build-release.yml](https://raw.githubusercontent.com/surge-synthesizer/surge/main/.github/workflows/build-release.yml)
- Surge XT's macOS build is signed "Developer ID Application: Paul Walker (547U7G7MZC)", that is, with a maintainer's individual Developer ID. Source: [Desktop Insights, Surge XT](https://desktopinsights.com/apps/surge-xt) (third-party scanner)
- plugdata: macOS .pkg built with `pkgbuild` and `productbuild`, signed with an individual's Developer ID ("Developer ID Application: Timothy Schoen"), notarized with `notarytool` and stapled; Windows .msi built with WiX 3.14. The Windows script contains a "Codesign Installer" comment, but no signing step appears in the workflow. Sources: [plugdata package-macOS.sh](https://raw.githubusercontent.com/plugdata-team/plugdata/develop/.github/scripts/package-macOS.sh); [plugdata package-Windows.sh](https://raw.githubusercontent.com/plugdata-team/plugdata/develop/.github/scripts/package-Windows.sh); [plugdata cmake.yml](https://raw.githubusercontent.com/plugdata-team/plugdata/develop/.github/workflows/cmake.yml)
- ChowDSP BYOD: macOS installer built with the third-party Packages tool (`packagesbuild`), shipped in a .dmg; Windows with Inno Setup 6; Linux as .deb. Sources: [BYOD build_mac_installer.sh](https://raw.githubusercontent.com/Chowdhury-DSP/BYOD/main/installers/mac/build_mac_installer.sh); [BYOD releases](https://github.com/Chowdhury-DSP/BYOD/releases)
- Dexed: ships a macOS .dmg and .zip, a Windows .exe and .zip, and a Linux .zip, with SHA-256 checksums. Source: [Dexed releases](https://github.com/asb2m10/dexed/releases)
- Airwindows: the developer wrote in 2021 that he wanted to keep shipping legacy Audio Units without code signing while working on signed builds; an Apple engineer advised signing and notarizing the final installer package. Source: [Apple Developer Forums thread 678085](https://developer.apple.com/forums/thread/678085) (2021, may be out of date)
- A KVR how-to thread on macOS notarization for plugins, apps and pkg installers has been maintained by developers since 2020 and reflects the same workflow: notarize the outer PKG or DMG and "everything inside will be notarized automatically". Source: [KVR, HOWTO macOS notarization](https://www.kvraudio.com/forum/viewtopic.php?p=7518248)

### Inferences
- Total yearly cost for a solo developer: 99 USD (macOS only, Windows unsigned or SignPath), about 219 USD (macOS plus Azure, USA and Canada only), about 170 USD in the first year (macOS plus Certum Open Source at 69 EUR), or roughly 300 to 400 USD (macOS plus a commercial OV certificate). These sums are my arithmetic from the cited prices.
- Peer practice suggests an order of priority: macOS notarization first (without it the installer is effectively blocked on macOS 15 and 26), Windows signing second (the unsigned installer still runs after two clicks, and signing does not remove the warning at first).
- Open source projects sign macOS builds under a named individual's Developer ID. There is no stigma or obstacle to a free plugin being signed by a person rather than a company.
- Making signing conditional on the secret being present (Surge, plugdata) keeps pull request and fork builds working. Worth copying.

### Gaps
- Whether current Windows installers of Surge XT, Dexed, plugdata and BYOD carry an Authenticode signature was not verified by downloading and inspecting them. plugdata's workflow shows no signing step; the others are unknown.
- Vital: the GitHub repository had no releases through the API, and its installers are distributed from the vendor's site; signing status not checked.
- Current Airwindows and Airwindows Consolidated signing status was not confirmed; the Dexed build workflow was not found at the path tried.
- No first-person write-up with a full itemized yearly budget from 2026 was found; the Moonbase article (2025) is the closest.

## 7. What users expect and complain about in plugin installation

### Takeaway
Users praise small, fast, plain installers with one screen and a clear choice, and they complain about vendor manager apps that stall, hide what they install, force everything at once, or cannot update one plugin. No measured drop-off rate for unsigned installers was found; the evidence that warnings cost installs is qualitative.

### Cited Findings
- KVR thread "Who has the worst plugin manager/install experience?" (January, year not shown on the page read; page 2 of 7): Native Access "used to blue screen my computer"; Plugin Alliance's manager was "functionally a disaster" because single plugins could not be updated (later improved); IK Multimedia's and Steinberg's managers were each called "the worst" by different users; UAD criticized for installing every plugin in the library; Cherry Audio's "stalls at around 14%". Praised: Audio Damage installers, "instantaneous and super easy to configure", one screen to pick formats; FabFilter, Spitfire, Waves Central ("dead simple"), Arturia ("pretty good"). Source: [KVR, Who has the worst plugin manager/install experience?](https://www.kvraudio.com/forum/viewtopic.php?p=9182272)
- Wants expressed in the same thread: per-plugin updates with change information, accurate update status, no forced downloads, choice of install drive or path, simple installers. Source: [KVR thread](https://www.kvraudio.com/forum/viewtopic.php?p=9182272)
- Native Instruments' own forum has long-running "issue with the installer service" and "installation failed" threads; users report that standalone component installers work when the manager fails. Sources: [NI community 41104](https://community.native-instruments.com/discussion/41104/native-access-wont-install-plugins-complains-about-no-access); [NI community 36520](https://community.native-instruments.com/discussion/36520/installation-failed-installation-failed-installation-failed)
- Format choice: FabFilter users asked to choose formats in the installer; a FabFilter representative replied that it is not currently possible because the macOS installer design they use offers only one customizable option. Source: [FabFilter user forum](https://prod.fabfilter.com/forum/add-comment?id=7952) (undated in what I saw)
- Uninstalling on macOS is an unmet need served by third parties: Wide Blue Sound's free Audio Plugin Uninstaller "reads the installation receipts and reverses the process" and filters by format; open source `unplugin` moves plugin files to the Trash. Sources: [KVR news, Wide Blue Sound Audio Plugin Uninstaller](https://www.kvraudio.com/news/wide-blue-sound-releases-free-audio-plugin-uninstaller-for-macos-58543); [unplugin on GitHub](https://github.com/teebs4140/unplugin)
- Friction of warnings: Apple DTS writes "It's important that your code pass Gatekeeper. If not, you're likely to lose a lot of customers, and your users' hard-won trust." Source: [Apple Developer Forums thread 706414](https://developer.apple.com/forums/thread/706414)
- A developer who paid for Windows signing reported that new users still saw the blue SmartScreen warning and that it hurt activation, without giving figures. Source: [Indie Hackers post](https://www.indiehackers.com/post/we-paid-for-windows-code-signing-and-new-users-still-see-a-scary-blue-warning-d3dab1188f)
- Microsoft's advice for new apps: "let beta users know they may see a SmartScreen prompt on first download". Source: [Microsoft Learn, SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
- SignPath Foundation makes an uninstall path a condition of signing: software with installation tools "must also provide uninstallation". Source: [SignPath Foundation terms](https://signpath.org/terms)

### Inferences
- The product's helper app is, in effect, a small plugin manager. The complaints above give its acceptance tests: fast, works offline, shows exactly which files it wrote and where, lets the user pick formats, can remove one generated plugin without touching the others, and never rescans or re-downloads everything.
- A macOS .pkg leaves receipts but has no built-in uninstall. Since the helper app creates plugins, it is the natural place for "remove this plugin" and "remove everything", which also answers the uninstall expectation on macOS and Linux. On Windows the Inno Setup uninstaller should also remove generated plugins or say clearly that it does not.
- Until installers are signed, the download page should show the exact dialogs and clicks for each system (System Settings, Privacy & Security, Open Anyway on macOS 15 and 26; More info, Run anyway on Windows). Peer projects do this, and Microsoft recommends telling early users.

### Gaps
- No quantitative data on abandonment at Gatekeeper or SmartScreen prompts for legitimate software was found. The only number located (99 percent of IE9 users declining a flagged download, Microsoft 2010) concerned malware and does not apply.
- Reactions to Arturia Software Center, Plugin Alliance Installation Manager and Splice were only covered through one KVR thread page; Splice and iLok were not mentioned there. Gearspace and Reddit threads were not read.
- Explicit user statements on uninstall expectations were not found; the inference rests on the existence and coverage of third-party uninstaller tools.
- The KVR thread's year was not visible; it is recent enough to mention the Plugin Alliance manager's later improvement.

## 8. Naming, identifiers and trademarks when users generate and redistribute plugins under the maker's manufacturer name

### Takeaway
Apple no longer runs a registry for Audio Unit manufacturer codes; pick a four-character code with at least one capital letter and check for collisions yourself. VST3 class IDs and CLAP IDs are self-assigned. The trademark that needs care is "VST": using the name or logo is optional under the MIT-licensed SDK, but if used it must follow Steinberg's rules. No source was found on trademark exposure from user-generated plugins carrying the maker's name; that part is unconfirmed.

### Cited Findings
- "Apple hasn't maintained an official manufacturer code registry for quite some time and unfortunately that documentation is stale." Advice in the same answer: choose a code related to the company name, check for conflicts against known vendors, avoid all-lowercase codes (reserved for Apple) and "Demo". Source: [Apple Developer Forums thread 38058](https://developer.apple.com/forums/thread/38058) (accepted answer, March 2016, by a forum member not identified as Apple staff)
- Older mailing list posts (2004 to 2015) pointed developers to Apple's data type registration page, and conflict on whether it ever covered Audio Unit manufacturer IDs. Source: [coreaudio-api list, June 2015](https://lists.apple.com/archives/coreaudio-api/2015/Jun/msg00022.html)
- Logic Pro and auval enforce the capital-letter rule in practice: an exported plugin was flagged until its plugin ID and manufacturer ID contained an uppercase character. Source: [KVR, PNS export thread](https://www.kvraudio.com/forum/viewtopic.php?p=8461654) (2022-06-27)
- VST3: the first plug-in found for a given Processor UID wins, so two different plugins sharing a class ID shadow each other. Source: [Steinberg VST 3 Developer Portal, Plug-in Locations](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical+Documentation/Locations+Format/Plugin+Locations.html)
- VST trademark: "Trademark usage (e.g. "VST" name or logo) is optional under MIT license", but any use must follow Steinberg's rules. If used: "VST" in plain text only (for example "MyCoolEngine for VST"), with the VST Compatible logo nearby; "VST" may not appear in a company name or company logo; derived forms such as "VSTi" are not permitted; first use carries the registered mark; credits must include "VST is a registered trademark of Steinberg Media Technologies GmbH." Source: [Steinberg VST usage guidelines](https://steinbergmedia.github.io/vst3_dev_portal/pages/VST+3+Licensing/Usage+guidelines.html) (fetched 2026-11-21)
- "Since version 3.8, VST 3 is licensed under MIT license." Source: [Steinberg VST 3 Developer Portal, VST 3 License](https://steinbergmedia.github.io/vst3_dev_portal/pages/VST+3+Licensing/VST3+License) (seen via search summary)
- Local check: the project's validation calls `auval -v <type> <subtype> PlPg`, so the Audio Unit manufacturer code in use is `PlPg`, which satisfies the capital-letter rule. Local file scripts/plugin.py, no URL.

### Inferences
- Every generated plugin shares the manufacturer code `PlPg` and differs by subtype, so the four-character subtype must be unique per generated plugin on a machine, and ideally stable for the same recipe across machines so shared projects reopen. Deriving the subtype, the VST3 class ID and the CLAP ID deterministically from the recipe identity gives both properties. Collisions between different users' plugins with the same derived code are possible with only four characters; this is a design risk, not a sourced fact.
- Because a VST3 host keeps the first plugin found for a class ID, a generated plugin that reuses the template's ID would be hidden by it (or hide it). The helper must write a fresh ID for each.
- All generated plugins appear in hosts under the maker's manufacturer name. If users pass them around, the maker's name is attached to plugins the maker never reviewed. A separate displayed vendor string such as "Made with Plugin Playground", terms of use for the name, and avoiding other companies' product names in presets or generated plugin names would reduce confusion. This is reasoning, not legal advice, and no precedent was found.
- Avoid "VST" in the product name, company name and logos, and add the Steinberg attribution line wherever the word VST3 appears on the site. "Audio Unit" and "Logic Pro" are Apple marks, and "CLAP" is an open standard with its own logo; their usage rules were not researched here.

### Gaps
- No current Apple statement (2020 or later) on manufacturer code registration was found; the 2016 forum answer is the latest evidence and is not from identified Apple staff.
- No source addresses trademark or liability questions for a tool whose users generate and redistribute plugins under the tool maker's manufacturer name. Blue Cat's Plug'n Script lets exporters set their own manufacturer name and ID, which sidesteps the question, but I did not confirm that from its manual.
- CLAP ID conventions (reverse-domain style identifiers) and CLAP logo or naming rules were not fetched from the specification in this session.
- Whether Steinberg's usage guidelines bind a GPLv3 project is disputed in a Steinberg forum thread and unresolved. Source for the dispute: [Steinberg forums, Cannot use the GPL3 option](https://forums.steinberg.net/t/cannot-use-the-gpl3-option/750876)
